# Agent 初学者 7 天学习计划

本计划把《poi-agent一周学完agent.pdf》中 `5 天 x 8 小时` 的路线展开为 7 天，目标不是在一周内记住所有术语，而是完成一个可运行、可测试、可解释的本地 Coding Agent 最小闭环。

## 来源标记

- **[PDF]**：来自 PDF 的主题、示例或学习顺序，括号中给出页码。
- **[补充]**：为保证初学者能真正运行、验证和面试表达而增加的工程实践。
- PDF 中过度简化的定义不直接作为学习结论，详见 [CONCEPT_CORRECTIONS.md](./CONCEPT_CORRECTIONS.md)。

## 先看整体架构

七天只围绕一条逐步扩展的数据流：

```text
用户任务
  -> Agent 循环（理解任务、选择动作、判断是否结束）
      -> 模型或离线 Mock
      -> 工具（read/search/edit/bash）
      -> 本地知识检索
      -> Context / Memory
  -> diff、测试结果、执行轨迹、最终报告
```

学习顺序是：先跑通模型调用，再组合 Node/Workflow，然后加入循环和工具，之后补检索、上下文、安全、评测。不要在第一天同时引入向量数据库、MCP、多 Agent 和复杂前端。

## 一周结束时的交付物

- 一个能在指定临时工作区内读取、搜索、修改文件并运行受限命令的本地 Coding Agent。
- 一个不依赖付费 API 的离线演示路径：Mock 模型或固定动作脚本也能跑通核心状态机和工具测试。
- 10 到 20 个固定小任务组成的评测集，以及成功率、失败原因和改进记录。
- 一份架构说明、一次 2 到 3 分钟演示、至少一个失败案例复盘。

## 第 1 天：环境与最小模型调用

### 目标

- 跑通 `uv` 项目环境和最小模型调用。
- 分清 Agent 程序、模型服务和工具执行三个边界。
- 即使没有可用 API，也能用 Mock 返回完成后续开发。

### 核心概念

- **[PDF, p1]** Python、`uv`、`OPENAI_API_KEY`、`OPENAI_BASE_URL` 和 `core/llm.py`。
- **[补充]** 消息输入/模型输出、模型适配层、环境变量、超时、错误分类、Mock 模型。
- **[补充]** “代码是否正确”和“外部模型是否可用”是两种不同验证。

### 动手任务

1. 阅读项目 README 和模型适配层，只画出调用链，不急着逐行理解。
2. 用 `uv sync` 安装项目依赖，确认解释器来自当前项目环境。
3. 使用环境变量配置模型地址和密钥；密钥只放在本地环境或未提交的 `.env` 中。
4. 运行最小模型调用，记录成功输出，或记录 HTTP 状态码、超时、鉴权等明确错误。
5. 增加一个 Mock 模型：输入固定消息，返回固定文本或预设工具调用，用它验证程序主流程。

### 验收标准

- `uv run` 可以启动程序，没有依赖或解释器错误。
- 真实模型或 Mock 至少有一条路径能稳定返回结构化结果。
- 删除模型密钥后，程序给出可理解的配置错误，而不是长堆栈或静默失败。
- `git status` 中没有密钥、`.env` 或无关生成文件。

### 常见坑

- 把密钥写入源码或提交到 Git。
- 把 `base_url`、模型名和 API 协议混为一谈。
- 外部 API 不可用时直接判断整个项目坏了。
- 第一天就加入多个供应商 SDK，导致错误来源无法定位。

### 预计时间

约 4.5 小时：架构阅读 1 小时，环境与调用 2 小时，Mock 和错误处理 1.5 小时。

## 第 2 天：从 Node 到 Workflow

### 目标

- 理解 Node 如何把一个大任务拆成可组合步骤。
- 实现并测试一条确定性的串行 Workflow。
- 能用自己的话说明每一步输入、输出和失败方式。

### 核心概念

- **[PDF, p1-p2]** Node 抽象；三个 Node 组成“接收输入 -> 搜索 -> 模型总结”；`workflow = node + node`。
- **[补充]** 状态对象、节点契约、串行控制流、错误传播、可观察日志。
- **[补充]** Workflow 的步骤通常由程序预先确定；Agent 的动作更多由运行时状态和模型选择。

### 动手任务

1. 阅读 `core/node.py` 和 `examples/workflow`，给每个节点写下输入、输出、副作用。
2. 运行原始 Workflow，并保存一条完整轨迹。
3. 把例子改造成“读取本地说明 -> 搜索关键词 -> 生成摘要”，避免把联网搜索作为唯一成功路径。
4. 为正常输入、空输入、节点异常各写一个测试。
5. 在日志中加入 `task_id`、节点名、开始/结束、耗时和错误类型，不记录密钥与敏感原文。

### 验收标准

- 能画出 Workflow 数据流，并指出状态在哪一步发生变化。
- 三个测试可重复通过；节点失败时后续节点不会继续误执行。
- 替换其中一个节点时，其他节点不需要大规模修改。
- 日志足以判断失败发生在哪个节点。

### 常见坑

- 每个 Node 都直接读取全局变量，表面拆分、实际强耦合。
- 一个节点同时负责检索、生成、落盘和展示。
- 捕获异常后返回空字符串，导致后续步骤把失败当成功。
- 只跑示例，不做任何小改动和错误实验。

### 预计时间

约 5 小时：代码与数据流 1.5 小时，改造 2 小时，测试和日志 1.5 小时。

## 第 3 天：从 Chatbot 到 Agent 工具循环

### 目标

- 实现“模型选择工具 -> 执行工具 -> 把结果交回模型 -> 判断结束”的循环。
- 用最小工具集完成一次真实文件任务。
- 给循环设置明确的安全和停止边界。

### 核心概念

- **[PDF, p2]** `chatbot = workflow + loop`；`agent = chatbot + tools`；示例 `examples/chatbot` 和 `examples/chatbot_with_tools`。
- **[PDF, p3]** 优先使用少量通用工具，如 read、write、edit、bash。
- **[补充]** Tool schema、参数校验、Observation、最大步数、重复动作检测、最终答案条件。

### 动手任务

1. 先运行 Chatbot，定位循环状态、历史消息和退出条件。
2. 只实现或启用 `read`、`search`、`edit`、受限 `bash` 四类能力。
3. 所有写入限制在专用临时目录；编辑前读取，编辑后生成 diff。
4. 设置最大步数、单工具超时、最大输出长度和重复调用保护。
5. 完成一次“读取文件 -> 修改一处 -> 运行测试 -> 汇报 diff 和测试结果”的任务。
6. 用 Mock 模型预设工具序列，为循环和失败分支写测试。

### 验收标准

- Agent 能完成一次端到端文件任务，并留下可读执行轨迹。
- 越界路径、未知工具、非法参数和超时命令都会被拒绝或终止。
- 达到最大步数时程序能正常收口，不会无限循环。
- 最终报告区分“已执行并验证”和“模型建议但未执行”。

### 常见坑

- 把整段 shell 字符串交给系统执行且没有范围限制。
- 工具失败后仍把结果标成成功。
- 每轮把巨量工具输出原样塞回上下文。
- 用工具数量衡量 Agent 能力，而不是任务成功率。

### 预计时间

约 6 小时：循环理解 1.5 小时，工具闭环 3 小时，边界与测试 1.5 小时。

## 第 4 天：检索、Context 与 Memory

### 目标

- 让 Agent 能从本地资料中找证据，而不是只依赖模型记忆。
- 控制长对话和长工具输出对上下文的占用。
- 建立可衡量的检索与记忆效果。

### 核心概念

- **[PDF, p2]** Chroma、Embedding 模型和 RAG。
- **[PDF, p3]** 短期 Context、长期 Context、对早期对话做总结压缩。
- **[补充]** 文档解析、切块、关键词/BM25 检索、向量检索、Top-K、引用、重排。
- **[补充]** Memory 的写入、选择、召回、更新、删除和来源追踪。

### 动手任务

1. 准备 5 到 10 个本地 Markdown 或代码文件，人工写出 10 个问题及期望证据。
2. 先实现关键词或 BM25 检索；Embedding/Chroma 作为可替换增强，不作为唯一方案。
3. 返回结果时保留文件名、位置、得分或命中原因，再让模型基于证据回答。
4. 为工具长输出增加截断和摘要，为早期对话增加压缩；关键约束单独保留，不能只存在于摘要中。
5. 比较无检索、关键词检索、向量检索在固定问题集上的命中情况。

### 验收标准

- 10 个问题均能输出可定位证据；统计 Top-K 命中率，而非只凭观感判断。
- 没找到证据时明确回答“未找到”，不编造文件内容。
- 长对话压缩后，任务目标、修改范围和安全限制仍被保留。
- 没有 Embedding API 时，离线检索路径仍可运行。

### 常见坑

- 把 RAG 直接等同于 VectorDB。
- 文档解析和切块质量很差，却只调相似度参数。
- 只返回生成答案，不保存检索证据。
- 摘要多次覆盖后丢失用户约束、失败记录或待办事项。

### 预计时间

约 5.5 小时：数据与问题集 1 小时，检索 2.5 小时，Context/Memory 1.5 小时，对比记录 0.5 小时。

## 第 5 天：Tool、MCP、Skill 与安全边界

### 目标

- 在整体架构中定位 Tool、MCP 和 Skill，而不是只背一句定义。
- 为本地工具建立最小权限、审批、超时和审计机制。
- 理解容器能解决什么，不能解决什么。

### 核心概念

- **[PDF, p2-p3]** Tool、MCP、Skill 的演进；渐进式加载；减少无用工具描述；代码执行优先。
- **[PDF, p4]** Docker 可用于大多数入门级 Sandbox 实践。
- **[补充]** MCP client/server、能力发现、传输、生命周期；Skill 的说明/资源/脚本包；策略层与执行层。
- **[补充]** 路径边界、命令白名单、环境变量过滤、资源上限、网络策略、人工确认和审计日志。

### 动手任务

1. 画出 Agent 直接调用本地 Tool 与通过 MCP client 调用 MCP server 的两条路径。
2. 把工具注册信息从主循环中分离，支持按任务只暴露必要工具。
3. 为文件工具增加规范化路径检查，为命令增加 allowlist、超时和输出上限。
4. 增加 `dry-run` 或执行前摘要；高风险写入必须先展示目标和 diff。
5. 编写至少 8 个拒绝测试：路径穿越、未知命令、超时、超长输出、缺失参数等。
6. Docker 只作为用户自行准备后的增强实验；无 Docker 时仍完成应用层安全测试。

### 验收标准

- 能解释 Tool、MCP、Skill 在当前项目中的位置和差异。
- 安全测试全部通过，危险请求有明确拒绝原因。
- 日志能回答谁在何时以什么参数调用了哪个工具、结果如何。
- 能说明“运行在容器中”不等于自动获得完整安全隔离。

### 常见坑

- 把 MCP 仅理解成“远程函数调用”，忽略协议和生命周期。
- 把 Skill 仅理解成本地函数，忽略指令、资源和渐进加载。
- 默认开放完整 shell、工作区外路径、网络和宿主环境变量。
- 认为 Docker 本身足以阻止所有逃逸、数据泄漏和资源滥用。

### 预计时间

约 5.5 小时：概念与架构 1.5 小时，策略实现 2.5 小时，拒绝测试 1.5 小时。

## 第 6 天：做成可评测的本地 Coding Agent

### 目标

- 把前五天的零散能力收成一个可演示项目。
- 用固定任务评测效果，而不是靠一次成功演示证明质量。
- 建立失败可定位、结果可复现的工程证据。

### 核心概念

- **[PDF, p3-p4]** 推荐实现 kimi-cli 或 pi-mono 类 Coding Agent；关注 Agent 效果评估和提示词优化。
- **[补充]** `inspect -> plan -> edit -> test -> report` 状态机、patch/diff、trace/replay、任务基准、确定性测试。
- **[补充]** 任务成功率、工具错误率、平均步数、耗时、成本和安全违规数。

### 动手任务

1. 将项目范围固定为：在专用工作区内定位问题、生成最小修改、运行测试、输出报告。
2. 保存每一步输入摘要、动作、工具结果、耗时和最终状态；敏感信息必须脱敏。
3. 准备 10 到 20 个小任务，覆盖读取、搜索、单文件修改、测试失败、越界拒绝。
4. 先用 Mock 或预设动作测试状态机，再选择性使用真实模型测试自主决策。
5. 统计指标，并挑一个失败任务做根因分类：模型判断、工具、上下文、环境或任务定义。
6. 只针对明确失败模式调整提示词或工具，不做无指标的“凭感觉优化”。

### 验收标准

- 全新环境可通过一条文档化命令运行离线演示和测试。
- 固定任务集有首轮基线；建议目标为至少 70% 成功，但必须如实报告实际结果。
- 所有修改都有 diff，所有“通过”都有测试或可观察证据。
- 相同失败能够通过 trace 定位，不需要重新猜测整个过程。

### 常见坑

- 直接复刻大型开源项目，自己无法解释关键取舍。
- 只展示成功样例，隐藏失败和安全边界。
- 把 Prompt 改长当作优化，却没有对照任务集。
- 将外部 API 波动、测试环境错误和 Agent 逻辑错误混成一个指标。

### 预计时间

约 7 小时：范围收口 1 小时，闭环实现 3 小时，任务集与评测 2 小时，失败复盘 1 小时。

## 第 7 天：Multi-Agent 取舍与面试收口

### 目标

- 理解什么时候使用 Subagent 或 Agent Team，什么时候保持 Single Agent。
- 把项目整理成可复现、可讲清、不过度宣传的面试材料。
- 完成一次从空环境启动到结果展示的演练。

### 核心概念

- **[PDF, p3-p4]** Multi-Agent 用于上下文隔离和压缩结果；Subagent；并行 Agent Teams；面试关注项目、评测、提示词优化、Sandbox。
- **[补充]** 任务依赖图、并行/串行、写入隔离、worker 结果协议、冲突处理和成本收益判断。
- **[补充]** 面试还可能考察编程基础、系统设计、调试、安全、测试和项目真实性。

### 动手任务

1. 先用 Single Agent 跑固定任务，记录成功率、步数和耗时作为基线。
2. 只选择两个互不写同一文件的任务做并行实验，例如“只读代码调查”和“只读测试分析”。
3. 规定 worker 只返回：结论、证据、修改建议、验证结果、阻塞项；不回传全部工具日志。
4. 对比 Single Agent 与并行方案的质量、耗时、成本和冲突，结果不更好就保留 Single Agent。
5. 完成 README：问题、架构图、数据流、边界、运行命令、评测、失败案例和下一步。
6. 准备 2 到 3 分钟演示和面试回答：为何轻框架、为何只用这些工具、如何限制风险、如何证明效果。

### 验收标准

- 能根据任务依赖解释并行和串行选择，不使用“Agent 越多越好”的理由。
- 并行实验无共享写入冲突，结果能由主流程验证。
- 从全新 clone 到离线演示有可复制步骤，现场不依赖付费 API。
- 简历和演示中的每个指标、功能和结果都能在仓库中找到证据。

### 常见坑

- 为展示 Multi-Agent 而强行拆分一个很小的串行任务。
- 多个 Agent 同时修改同一文件，却没有隔离和合并策略。
- 只讲框架名和热门术语，不讲数据流、失败和取舍。
- 宣称“面试只问项目”或把一次 demo 成功写成稳定生产能力。

### 预计时间

约 6.5 小时：并行实验 2 小时，文档与评测整理 2.5 小时，演示和问答 2 小时。

## 学习结果判断

一周结束时，不要求复刻完整的 kimi-cli 或 pi-mono。满足以下条件，才算真正完成入门：

- 能从用户任务讲清 `Agent -> 模型/工具 -> Observation -> 下一步 -> 最终结果` 的数据流。
- 能在没有付费 API 的情况下验证状态机、工具、安全边界和大部分测试。
- 能展示一个真实成功案例和一个真实失败案例。
- 能明确区分 PDF 的入门类比、自己的工程补充和仍未验证的设想。
