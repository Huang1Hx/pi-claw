# Iteration 017：十任务当前模型端到端基线

## 状态

已批准待提交。本轮只记录产品评测代码、可复现命令与脱敏结果。原始工作区、模型
回复和 Trace 位于 Git 忽略的 `runs/`，不会提交远程。

## 基线、目标与边界

代码基线为 `639a322`。本轮把原先 2 个任务、每任务 2 次的 12-trial 小样本扩展为 10 个中等
复杂度纯函数修复任务，每任务独立重复 3 次，同时比较：

1. 单 Agent；
2. 当前规划—编码—审查工作流；
3. 主 Agent＋两个独立只读子 Agent。

主批次使用 grader 2.0，共 `10 × 3 × 3 = 90` 个真实 trial。它测量当前配置下的端到端结果：
Provider 或网络失败
也进入失败分母。工作流继承生产 `premium_review_policy=risk`，所以高风险或多轮返工任务必要时
可调用 `kimi-k3`；这使结果反映实际部署策略，但也意味着它不是只改变协调方式的纯因果实验。

测试锁定，避免前一个 trial 污染后一个 trial。

## 指标口径

- 严格成功：执行、Trace、夹具、最终文件、固定公开测试和全部隐藏语义检查同时通过。
- `pass@3`：某任务三次中至少一次成功的任务比例。
- `pass³`：某任务三次全部成功的任务比例，即重复成功率。
- P50 使用中位数，P95 使用最近秩真实观测值；失败 trial 同样计入延迟。
- Token 包含规划、编码、常规审查、Kimi 高级审查、子 Agent和返工。
- 已路由但未返回 usage 的请求只记缺口，不按零 Token 处理。
- 越权次数是被 Policy/审批拒绝的副作用尝试，不表示越权已经成功。
- 原始 `report.json` 含逐 trial 路径；`public-summary.json` 只保留白名单聚合字段。

## Provider 故障与补充批次

主批次没有 trial 达到 420 秒 deadline，但出现 22 个 provider_error：前段 6 次读取超时，后段
16 次 DNS 解析失败。失败仍进入主指标，不重跑替换。

网络恢复后对 Worker 分配和版本更新另跑 18 个补充 trial。前两个 trial 能完成，随后学校端点
返回请求级 HTTP 429；补充批次最终 2 个 completed、16 个 provider_error、16 个 usage 缺口。
这份补充样本不替换主批次，只证明当前执行器缺少共享请求节流/退避，`workers=2` 只限制 trial
并发，不能限制多个 Agent 阶段在服务端时间窗口内的总请求速率。

## 结论与下一阶段

在这次配置和外部服务状态下，单 Agent 的严格成功率、pass@3、pass³、P50 和每成功 Token 均
优于另外两种模式；当前证据不支持“多 Agent 天然更可靠”。主从模式证明了只读子 Agent、唯一
写者和零写冲突边界，但增加了端到端耗时和 Token，且没有换来更高严格成功率。

结果不能外推为通用架构排名：工作流在必要时使用 Kimi，三种模式并非相同模型调用图；任务只有
十个受限纯函数；后两项被外部 Provider 故障污染。阶段 3 应先处理共享请求节流、429 Retry-After、
DNS/读取超时分类、取消传播和重复循环，再用同一任务做修改前后对照，而不是立即增加更多 Agent。
