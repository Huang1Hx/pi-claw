# Trace 驱动评测合并与候选修复设计

## 背景与目标

阶段二已有一份完整的 90-trial 基线报告，以及一份只重跑
`dependency_order` 的 9-trial 报告。后者使用了更新后的评分器，但两份结果尚未形成一份
同口径的 90-trial 报告。同时，现有失败只能人工查看 Trace，尚不能自动把失败证据反馈给
同一架构继续修复候选 `solution.py`。

本次实现两个能力：

1. 离线、可审计地把目标子集结果替换进完整基线，并用当前评分器重评其余 trial。
2. 从合并报告选择可修复失败，创建干净工作区，向原架构提供脱敏 Trace 证据，最多修复两轮。

## 不做什么

- 不自动修改评分器、隐藏用例、任务规格或 Pi-Claw 自身源码。
- 不把 `provider_error` 当成语义失败交给 Agent 修复；它只能走传输续跑机制。
- 不覆盖任何来源报告、trial 目录或 Trace。
- 不把隐藏评分的 expected/actual、API Key、模型 URL 或用户绝对路径暴露给模型。
- 不把修复后成功率冒充首次成功率。

## 产物与不可变性

每次合并写入一个全新目录：

- `manifest.json`：来源路径、来源文件 SHA256、替换身份、评分器版本与合并规则。
- `report.json`：同一任务/模式/trial 身份下的完整重评报告。
- `public-summary.json`：不含本机路径和逐 trial 证据的可公开聚合摘要。
- `grader-calibration.json`：本次评分器校准结果。

每次修复也写入全新目录：

- `manifest.json`：基线来源及其 SHA256、轮数上限、选择规则与模型配置。
- `round-N/<mode>/<task>-<trial>/`：干净任务文件、上一轮 `solution.py`、Trace、评分和轮次元数据。
- `repair-ledger.json`：每个身份的父结果、每轮状态、Token、耗时、Trace 和最终状态。
- `report.json`：首次指标、修复后指标、恢复率、增量成本与未恢复失败分层。
- `public-summary.json`：去除本地路径后的公开指标。

来源文件在开始与结束时都计算 SHA256；若执行期间变化则停止生成最终报告。

## 稳定身份与合并规则

trial 身份固定为 `(mode, task, trial)`：

- `mode` 必须是 `single`、`workflow`、`team`。
- `task` 必须存在于当前任务目录。
- `trial` 必须是 1–5 的整数。

合并时：

1. 来源与替换报告都不得包含重复身份。
2. 替换身份必须是来源身份的非空子集；未知身份立即报错。
3. 两份报告的模型分配、premium model、deadline、max steps 和 trials-per-task 必须一致。
4. 替换 trial 采用替换报告结果；其余 trial 从原工作区按当前评分器离线重评。
5. 重新计算全部 90 个 trial 的 `by_mode` 与 `by_mode_and_task`，不复用旧聚合值。
6. 记录来源与替换批次的实际采集成本，避免把 9 次重跑成本从总消耗中抹掉。

## 修复选择与干净工作区

候选必须同时满足：

- 首次严格评分失败；
- 状态不是 `provider_error` 或 `harness_error`；
- 来源工作区存在可读取的 `solution.py`；
- 身份合法且唯一。

每轮工作区从 `TASKS[task].files` 重新创建 `SPEC.md`、`test_target.py` 与初始文件，再只复制
父 trial 的 `solution.py`。因此即使上一轮修改了 fixture，也不会继承污染。修复保持原始
`mode`，让单 Agent、规划—编码—审查和主从 Agent 的恢复能力仍可比较。

## Trace 证据最小化

修复提示只包含：

- 失败检查的 `name` 与 `layer`；
- leader 的公开测试输出；
- 工具执行错误、权限审批错误和完成验证错误；
- 受限语法错误中的具体 AST 节点；
- 上一轮状态和轮次。

证据处理必须：

- 丢弃隐藏评分 `detail` 中的 expected/actual；
- 使用现有 `redact` 脱敏，再把来源工作区和用户目录替换为占位符；
- 只读取已登记的 Trace 路径，并限制总字符数为 8,000；
- 不包含 model prompt/reply 的完整正文，以免回放无关或敏感上下文。

## 修复循环

每个身份最多两轮：

1. 基于父 `solution.py` 和证据构建新工作区。
2. 用原 `mode` 运行一次完整 trial，仍遵守 420 秒墙钟上限和既有请求重试设置。
3. 当前评分器严格通过则停止；否则把本轮结果作为下一轮父结果。
4. `provider_error` 记录为传输失败，不生成语义反馈，也不伪装成零成本。

## 指标

最终报告同时展示：

- 首次严格成功率与成功数；
- 修复后严格成功率与成功数；
- 可修复失败数、恢复数与恢复率；
- 第 1/2 轮分别恢复的数量；
- 首次采集、替换采集、修复增量和总采集的已知 Token；
- 每个恢复 trial 的增量已知 Token；
- 首次与修复后的端到端耗时、provider error、越权、冲突与返工；
- 未恢复身份、失败层、最终状态和 Trace 路径。

Token 缺失继续显式标注为未知，所有“每成功 Token”均是已知 Token 的下界时必须保留该标志。

## 安全与可复现性

- 合并模式不调用模型、不要求 API Key。
- 修复模式必须显式传入 `--live`，避免误调用付费模型。
- Kimi 是否触发继续由现有 premium review 风险策略决定；报告单独核算其请求和 Token。
- 输出目录必须不存在，防止覆盖旧证据。
- 中断时终止所有 trial 进程组；已完成的轮次目录保留用于排查，但不生成伪完整汇总。
