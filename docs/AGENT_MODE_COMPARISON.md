# 单 Agent、顺序工作流与主从多 Agent 对照评测

本评测用同一批任务、相同起始文件、相同主提示、相同工具和相同外部评分器比较三种执行架构。
目标不是用少量任务给模型下通用排名，而是回答：增加规划/审查或独立子 Agent 后，严格成功率、
重复可靠性、端到端耗时和完整 Token 消耗发生了什么变化。

## 三种模式与模型分配

| 模式 | 参与者与当前模型 | 执行顺序 | 写权限 |
|---|---|---|---|
| `single` | 编码 Agent：`deepseek-flash` | 一个 Agent 自主读取、修改、测试 | 编码 Agent 是唯一写者 |
| `workflow` | 规划/编码/常规审查：`deepseek-flash` | 规划 → 编码/验证 → 审查；审查否决后有界返工 | 仅编码阶段的工具候选由外层 Agent 执行 |
| `team` | 主 Agent与两个独立子 Agent：`deepseek-flash` | 两个子 Agent 并行只读分析；屏障汇合后主 Agent 编码/验证 | 只有主 Agent 可写和运行命令 |

工作流继承生产 `premium_review_policy=risk`：权限等高风险任务或常规审查经历两轮返工时，可以
调用用户自费 `kimi-k3`。报告必须单列触发原因、尝试/已知请求数、Token 与 usage 缺口；Kimi
Token 同时属于工作流总消耗，不能重复相加。意图分类在本评测中固定为本地规则，不为分类额外
调用任何模型。

`team` 不是分布式系统：当前实现在单宿主线程池中运行，每个参与者拥有独立 Agent、Provider、
上下文和 Trace。两个子 Agent 结束后主 Agent 才启动，因此不存在多个写者并发修改。子 Agent
产物按不可信数据交接，单份有字符上限；主 Agent 必须重新核对文件。SessionStore 的文件锁没有
被用作多 Agent 调度锁，当前也不宣称跨进程/跨机器容错。

## 固定任务集

每个任务均只有 `SPEC.md`、带缺陷的 `solution.py` 和 `test_target.py`。三种模式收到完全相同的主
提示，只允许修改 `solution.py`，且只能运行下列命令。提示中明确列出有界纯函数语法，避免把
未公开的实现风格限制误算成模型失败：

```bash
uv run python -m unittest -q test_target.py
```

十项任务都属于中等复杂度的局部代码修复：包含多条相互作用的输入、原子性、顺序或稳定性规则，
但不依赖大型仓库知识、外部服务或长时间构建，适合在受控预算下重复比较架构差异。

| 任务 ID | 主要规则 |
|---|---|
| `inventory_reservation` | 库存校验、累计需求、原子预留 |
| `window_merge` | 排序、gap 合并、默认参数和输入不变性 |
| `permission_filter` | 权限过滤、稳定顺序、授权/请求去重 |
| `balance_transfer` | 顺序转账、到账复用、批次原子失败 |
| `dependency_order` | 稳定拓扑排序、循环/缺失/重复依赖 |
| `event_deduplication` | 精确事件契约、重复与冲突、稳定排序 |
| `rate_limit_window` | 只计已接纳请求、滑动边界和单调输入 |
| `config_overlay` | 两层副本、保护项、未知配置拒绝 |
| `worker_assignment` | 最小累计负载与稳定并列规则 |
| `versioned_update` | 乐观版本检查与批量原子更新 |

任务静态材料位于 `mode_task_catalog.py`，Agent 不可见的隐藏用例位于 `mode_cases.py`。每项参考
实现必须全部通过，初始缺陷必须至少失败一项；校准输入每次深拷贝，缺陷候选不能污染后续 trial。

## 公平性与严格评分

- 每个 trial 都复制全新的工作区；模式之间不共享模型上下文、最终代码或测试结果。
- 外部评分器先用参考实现和错误初始实现校准，再允许真实模型运行。
- 候选代码先经过有界 AST 检查：目标函数签名必须精确，可包含最多三个无递归纯辅助函数；
  禁止导入、顶层执行、不受控调用和 `while`；允许有明确上界的 `for` 以及其中的
  `break`/`continue`。拒绝结果会返回具体 AST 节点。这仍不是通用 OS 沙箱。
- 严格成功要求：Agent 终态为 `completed`、Trace 完整、主 Agent 真实跑过固定公开测试且成功、
  固定夹具未被修改、无额外文件、最终函数通过全部隐藏用例、所有输入保持不变。
- 模型的“已经完成”文字和审查者的“approve”都不能替代文件与测试证据。
- 各模式采用相同 `max_steps`、420 秒 trial 墙钟期限和普通模型单请求重试协议；每个 DeepSeek
  逻辑请求最多尝试 3 次，暂时性失败按 2 秒、4 秒指数退避，单次等待不超过 10 秒。Kimi profile
  继续用 `max_attempts=1` 覆盖全局值。顺序工作流自己的有界规划/审查/返工是被比较架构的一部分。

## 指标定义

设一个模式有 `N` 个 trial、严格成功数为 `S`，每个任务独立重复 `k` 次：

| 指标 | 计算与解释 |
|---|---|
| 严格成功率 | `S / N`；任何 gate 失败都进入失败分母 |
| 实测 `pass@k` | 对每个任务，k 次中至少一次成功的任务比例 |
| 实测 `pass^k` | 对每个任务，k 次全部成功的任务比例；即重复成功率 |
| 端到端耗时 | 从该 trial 启动到全部参与者结束；`team` 包含并行子 Agent 和主 Agent |
| P50 / P95 | P50 为中位数；P95 为最近秩真实观测值；成功与失败 trial 都进入统计 |
| 总 Token | 所有已报告的输入+输出 Token；包含规划、编码、审查、全部子 Agent和返工 |
| 按模型 Token | 分 DeepSeek/Kimi 报告已知请求与 Token；路由后无 usage 的请求单列缺口 |
| 每个严格成功 Token | 该模式全部 trial（含失败、返工）的已知总 Token / `S` |
| 越权次数 | Policy/审批拒绝的调用；只读阶段/子 Agent 发起副作用候选也计入，按 participant+call_id 去重 |
| 写冲突次数 | 工具的修改前指纹与执行前指纹不一致，因目标文件已变化而拒绝的次数 |
| 返工次数 | 宿主拒绝完成，或顺序工作流审查返回 `changes_requested` 的次数 |

服务端没有返回 usage 时，该 trial 标为用量缺口，不把未知 Token 当零。期限终止时从每个参与者
Trace 的最后累计值恢复已完成请求的已知 Token，在途请求仍标为未知。报告给已知总量，并将
“每成功 Token”标成下界。学校平台模型不计算货币费用，但 Token 仍按上述方式统计，以衡量架构
开销。并行耗时不能用各参与者耗时简单相加，所以使用 trial 实际墙钟时间。

## 运行与产物

先仅校准评分器，不调用模型：

```bash
uv run --frozen python -m evaluation.compare_modes \
  --output runs/agent-modes-calibration
```

运行当前对照：10 个任务 × 3 次重复 × 3 种模式，共 90 个真实 trial：

```bash
uv run --frozen python -m evaluation.compare_modes \
  --live --config pi-claw.toml \
  --trials 3 --workers 2 --deadline 420 --max-steps 24 \
  --max-attempts 3 --retry-base-delay 2 --max-retry-delay 10 \
  --output runs/agent-modes-current
```

`deadline=420` 是整个 trial 的外层资源上限，不是单次 API 超时；模型 profile 当前为 120 秒。
三次完整读取超时加默认退避约为 366 秒，因此连续慢失败仍可能触发外层 deadline。该限制用于
阻止失控任务，不是“多阶段工作流一定有足够时间完成”的保证。

输出目录必须不存在。根目录包含 `manifest.json`、`grader-calibration.json`、`report.json` 和仅含
白名单聚合字段的 `public-summary.json`；
每个 trial 保留起始任务、脱敏配置摘要、日志、最终工作区、每个参与者的独立 Trace、运行结果和
逐项评分。`runs/` 被 Git 忽略；API Key、Base URL 和价格不会写入产物。

## 当前 90-trial 实测结果

2026-09-28 使用 grader 2.1 对 Iteration 017 的 22 个 `provider_error` 做身份保持的受控续跑；
语义失败、循环和未验证项不重跑。最终 90 条中没有 Provider 错误，详细恢复链、分任务结果与累计
获取成本见 [Iteration 018](iterations/ITERATION_018_PROVIDER_RECOVERY.md)。

| 模式 | 严格成功 | pass@3 | pass³ | P50 / P95 | 已知总 Token | 已知 Token/成功 | usage 缺口 | 越权 / 冲突 / 返工 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 单 Agent | 18/30（60.0%） | 80% | 50% | 64.253 / 211.616 s | 982,398 | 54,577.67 | 0/30 | 30 / 0 / 41 |
| 规划—编码—审查 | 10/30（33.3%） | 50% | 20% | 81.128 / 226.823 s | 2,356,069 | ≥235,606.90 | 1/30 | 18 / 0 / 3 |
| 主 Agent＋独立子 Agent | 13/30（43.3%） | 60% | 20% | 97.010 / 150.882 s | 1,531,647 | 117,819.00 | 0/30 | 21 / 0 / 6 |

最终终态为 68 个 completed、19 个 loop_detected、2 个 unverified 和 1 个 deadline；严格成功
`41/90`。最终选定 90 条包含已知 Token `4,870,114`，其中工作流 13 次 Kimi 请求均返回 usage，
已知 Kimi Token `162,337`。单 Agent 的成功率、重复成功率和效率仍最好，证据不支持“增加 Agent
数天然提升可靠性”。

最终能力表会用恢复结果替换同身份 Provider 失败，但工程成本不能删除旧尝试：从原始批次到四轮

`198,867`。因此架构能力指标和获取这份指标的实际成本必须分开阅读。

## grader 2.2 的 `dependency_order` 定向复测

旧 grader 2.1 的完整基线中，该任务 `0/9`，九份候选都使用任务规格未声明、评分器却禁止的
`while`。2.2 公开有界实现约束，允许 `for` 内 `break`/`continue`，仍禁止 `while`，并让审批失败
返回具体违规节点。随后只重跑 `dependency_order`，不回写上面的 90-trial 历史基线。

初次严格成功为 `6/9`：单 Agent `2/3`、工作流 `1/3`、主从 `3/3`；9 个候选的语法边界检查
全部通过。另有两个 DeepSeek `provider_error`，完成执行的 7 条中 6 条成功。随后使用有限重试
只续跑这两个身份，均严格通过；定向结果成为 `8/9`，只剩 workflow/trial 1 的语义失败。
初始 9 项加两次新补跑的实际获取成本为 11 个 trial-run、538,541 个已知 Token。完整过程与
边界见
[Iteration 019](iterations/ITERATION_019_DEPENDENCY_ORDER_BOUNDARY.md)。

## grader 2.2 合并与 Trace 驱动修复

2026-09-30 将上述 `dependency_order` 最终 9 项按 `(mode, task, trial)` 替换进完整基线，其余
81 项从原工作区用 grader 2.2 离线重评。合并后的首次严格成功为 `49/90`，随后只给失败候选
最多两轮脱敏 Trace 反馈：

| 模式 | 首次严格成功 | 修复后严格成功 | 恢复数 | 修复尝试 | 修复已知 Token |
|---|---:|---:|---:|---:|---:|
| 单 Agent | 21/30 | 25/30 | 4 | 14 | 1,837,237 |
| 规划—编码—审查 | 12/30 | 26/30 | 14 | 22 | 3,866,684 |
| 主 Agent＋独立子 Agent | 16/30 | 27/30 | 11 | 19 | 2,096,650 |

总计从 `49/90` 提升到 `78/90`；41 个首次失败恢复 29 个，第一轮恢复 28、第二轮恢复 1。
修复共消耗 7,800,571 个已知 Token，连同历史基线、定向补跑和被替代的网络失败，完整采集成本
为 13,209,226 个已知 Token。修复阶段调用 Kimi 6 次、已知 90,363 Token。

该结果不能回写成首次成功率：它测量的是获得失败层与公开执行错误后的恢复能力。workflow/team
恢复数更多，但消耗也更高；12 个未恢复项主要是非固定命令导致的审批循环和长尾，另有一个工作流
达到 36 次模型请求上限。自动修复只修改隔离工作区的 `solution.py`，不修改 grader、隐藏用例、
SPEC 或产品源码。血缘、逐轮成本、剩余 Trace 和命令见
[Iteration 021](iterations/ITERATION_021_TRACE_GUIDED_EVAL_REPAIR.md)。

## 历史 12-trial 小样本（不与当前基线混算）

2026-09-21 使用 grader 1.2 完整运行 12 个 trial。执行产物位于
`runs/agent-modes-final-20260921/`；正式汇总为 `report.json`，模型执行结束时的原始汇总另存
`report-execution.json`。严格成功结果没有在重评分时改变；重评分只把“路由已发起但超时而没有
usage”的请求改为显式缺口。

| 模式 | 严格成功 | 实测 pass@2 | 实测 pass² | 中位端到端耗时 | 已知总 Token | 已知 Token/成功 | 用量缺口 trial | 越权 / 冲突 / 返工 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 单 Agent | 2/4（50%） | 50% | 50% | 132.005 s | 42,316 | ≥21,158 | 1/4 | 0 / 0 / 0 |
| 规划—编码—审查 | 0/4（0%） | 0% | 0% | 140.405 s | 13,732 | 不适用 | 4/4 | 0 / 0 / 0 |
| 主 Agent＋独立子 Agent | 2/4（50%） | 100% | 0% | 264.207 s | 43,456 | ≥21,728 | 4/4 | 0 / 0 / 0 |

分任务结果：单 Agent 的库存任务 0/2、窗口任务 2/2；主从模式两个任务均为 1/2；顺序工作流
两个任务均为 0/2。主从模式因此覆盖了两个任务（pass@2=100%），但没有任务连续两次成功
（pass²=0%），不能称为稳定优于单 Agent。它的中位耗时约为单 Agent 的 2 倍，已知每成功 Token
也略高；两个只读子 Agent 的并行只覆盖探索阶段，主 Agent 编码仍串行。

顺序工作流 4 次均在 planner 阶段以读取超时结束，没有进入编码模型；较低 Token 不是效率优势，
而是提前失败。单 Agent 一次库存失败源于续接超时，另一次完成公开测试但漏掉两个严格容器类型
边界。主从的两次成功分别落在不同任务，另外两次为请求链超时。全部 12 次均为 0 写冲突、
0 越权、0 返工事件，说明唯一写者和只读子 Agent 边界有效，但不能证明分布式能力。

三种模式合计有 99,504 个服务端已报告 Token。另有 15 个已发起请求因超时没有 usage：单 Agent
1 个、顺序工作流 4 个、主从 10 个。因此总 Token 和每成功 Token 都只是已知下界，不能把未知
请求按零计，也不能据此计算精确费用。样本只有两个任务、每任务两次，结果反映当前学校接口和
当前模型配置，不外推为通用模型或架构排名。
