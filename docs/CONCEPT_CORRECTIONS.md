# 《一周学完 Agent》概念纠偏

这份文档不是否定 PDF 的入门价值。PDF 用很短篇幅给出了 `Node -> Workflow -> Chatbot -> Agent` 的实践主线，适合帮助初学者快速建立轮廓。但其中若干表达是作者观点或教学类比，不能直接当作行业定义、架构定律或面试事实。

## 快速结论

| PDF 中的简化或观点 | 更严谨的结论 | 对项目实践的影响 |
| --- | --- | --- |
| `RAG = VectorDB` | RAG 是“检索证据并用证据增强生成”的系统流程，VectorDB 只是可选检索组件 | 先验证解析、切块、召回和引用，不要先绑定向量数据库 |
| Tool 是 process call | Tool 是模型或 Agent 可选择调用的外部能力接口，不要求通过独立进程 | 明确 schema、权限、错误和副作用 |
| MCP 是 remote process call | MCP 是连接 AI 应用与外部能力的客户端-服务器协议，包含能力发现、调用和生命周期等约定 | MCP 不等于任意 RPC，也不保证工具安全或质量 |
| Skill 是 local process call | Skill 没有脱离具体平台的唯一行业定义；常见 Agent Skill 是可渐进加载的指令、资源和脚本包 | Skill 可以指导模型组合已有工具，不一定对应一个函数 |
| Agent 面试只问项目，没有八股 | 项目通常很重要，但岗位还可能考编程、系统设计、RAG、评测、安全、调试和基础知识 | 准备可验证项目，也要能解释底层取舍 |
| 优秀 Agent 都采用自建轻框架 | 自建、轻框架和成熟框架各有适用条件，不能由少量案例推出“都” | 按复杂度、可控性和维护成本选择 |
| Multi-Agent/Agent Teams 能成倍提高效率且不冲突 | 并行只在任务可拆分、依赖清楚、写入隔离时可能加速，并会增加协调成本 | 先做 Single Agent 基线，再用指标判断是否拆分 |
| Docker 作为 Sandbox 可应对绝大多数场景 | Docker 是重要隔离层，但不自动解决权限、网络、密钥、资源、镜像和宿主配置风险 | 仍需最小权限、资源限制、审计和人工确认 |

## 1. RAG 不等于 VectorDB

### PDF 表达

PDF p2 认为实际只需要检索，进一步写成“RAG = VectorDB”。这可以帮助初学者注意检索的重要性，但把完整系统缩成了一个存储组件。

### 严谨定义

RAG（Retrieval-Augmented Generation）至少包含以下数据流：

```text
数据采集/解析 -> 切块与索引 -> 查询理解 -> 检索/重排
-> 证据组织 -> 基于证据生成 -> 引用与效果评测
```

VectorDB 只可能承担“索引和向量相似度检索”的一部分。检索也可以使用：

- 关键词、倒排索引或 BM25；
- SQL、图数据库或业务 API；
- 文件搜索、代码符号索引；
- 向量与关键词结合的混合检索。

并非所有 RAG 都需要生成长答案。例如检索结果可以用于工具参数、决策或引用验证；但如果完全没有“用外部证据增强后续模型行为”，就不宜只因使用了 VectorDB 而称为完整 RAG。

### 工程判断

先问四个问题：原始内容是否正确解析？查询需要哪类检索？Top-K 是否找到正确证据？生成结果是否忠于证据？只有答案表明语义召回确有价值时，再引入 Embedding 和 VectorDB。

## 2. Tool 不是 process call 的同义词

### PDF 表达

PDF p2 把 Tool 概括成 `process call (function call)`。

### 严谨定义

在 Agent 系统中，Tool 更接近“通过结构化契约暴露给模型或控制器的能力”。它可能是：

- 当前进程内的普通函数；
- 子进程或命令行程序；
- HTTP/RPC 服务；
- 数据库、浏览器或人工审批动作。

Tool 的重点不是运行在哪个进程，而是契约和控制：名称、描述、输入 schema、输出结构、错误语义、权限、副作用、超时和可审计性。

### 工程判断

少量通用工具通常有利于降低选择难度，但“少”不是唯一目标。应该保留完成目标所需的最小能力集，并用任务成功率和安全测试评估，而不是机械删除工具。

## 3. MCP 不等于 remote process call

### PDF 表达

PDF p2-p3 将 MCP 类比为后端 RPC，并称为 Remote Tool。

### 严谨定义

MCP（Model Context Protocol）是 AI 应用连接外部能力的客户端-服务器协议。它规范的不只是“调用远程函数”，还包括能力协商与发现、工具等能力的描述与调用、消息传输和连接生命周期等。具体实现可以跨网络，也可以在本机通过标准输入输出连接，因此“remote”不是必要条件。

MCP 解决的是互操作接口问题，不自动保证：

- 服务返回的内容可信；
- 工具拥有合适权限；
- Prompt Injection 已被阻止；
- 所有客户端都会把全部工具描述放入每一次模型请求；
- 使用 MCP 一定比直接调用本地 Tool 更好。

不同客户端可以使用工具筛选、延迟发现、分组或渐进加载降低上下文开销。因此“所有 MCP 工具每轮都进入 Prompt”不是协议本身的必然要求。

### 工程判断

同进程内、只服务一个项目的简单能力，可先直接使用 Tool。需要跨客户端复用、清晰协议边界或独立服务生命周期时，再考虑 MCP。无论哪种方式，都要单独设计授权、输入校验、超时、审计和失败恢复。

## 4. Skill 不等于 local process call

### PDF 表达

PDF p3 把 Skill 写成 Local Tool，并强调渐进式加载和代码执行。

### 严谨定义

“Skill”不像 MCP 那样仅凭一个词就有统一、脱离平台的协议定义。以常见的 Agent Skill 形态看，它通常是一个可按需加载的能力包，可能包含：

- 使用条件和步骤说明；
- 领域规则与参考资料；
- 模板、示例或资源；
- 可调用脚本。

Skill 可能指导 Agent 组合多个已有 Tool，也可能根本不执行本地函数。渐进加载可以减少无关上下文，但是否节省 Token、如何加载，仍取决于宿主 Agent 的实现。

### 工程判断

当能力主要是“可复用流程和知识”时使用 Skill；当能力是一个结构化动作时使用 Tool；当能力需要通过标准客户端-服务器边界被多个应用连接时考虑 MCP。三者可以组合，不能简单按本地/远程互斥分类。

## 5. “Agent 面试只问项目”不是可靠事实

### PDF 表达

PDF p4 写道“agent 面试只问项目，没有八股”。这更像强调项目重要性的建议，不是所有公司和岗位的统一规则。

### 更现实的准备范围

面试可能同时覆盖：

- 项目真实性：本人做了什么、为什么这样设计、失败过什么；
- 编程与调试：Python、异步、异常、测试、Git、Linux；
- Agent 架构：循环、工具、Context、Memory、停止条件；
- RAG 与评测：召回、引用、测试集、指标、回归；
- 系统与安全：并发、超时、幂等、权限、Sandbox、Prompt Injection；
- 模型工程：Prompt、结构化输出、成本、延迟、供应商切换。

一个真实项目仍是最好的主线，但项目必须能把这些问题串起来。不要背框架 API；也不要因为 PDF 的说法而完全不准备基础知识。

## 6. 轻框架不是唯一正确选择

### PDF 表达

PDF p2 推荐自己搭建轻框架，并对 LangChain 等重框架持强烈否定态度。

### 严谨判断

轻框架的优势是数据流清楚、依赖少、便于定制和调试，特别适合学习、核心路径和受控原型。成熟框架的优势可能包括现成集成、可观测性、团队统一接口和社区支持。两者都可能被误用。

选择时应比较：

- 是否能看清并控制核心循环；
- 是否需要大量现成连接器；
- 依赖升级和安全维护成本；
- 团队是否已有运行经验；
- 是否容易测试、追踪和迁移。

某个框架曾有安全漏洞，不足以单独证明所有版本、所有模块或整个架构路线都不可用。正确做法是检查受影响范围、升级版本、减少攻击面并持续维护依赖。

## 7. Memory 不只是短期加长期 Context

### PDF 表达

PDF p3 用“短期 Context + 长期 Context”快速介绍 Memory。

### 严谨定义

这是一个入门类比，不是完整实现。可用 Memory 还需要回答：

- 什么信息值得写入，谁有权写；
- 何时召回，如何排序和去重；
- 信息来源是否可追踪；
- 过期或错误记忆如何更新、删除；
- 用户隐私、租户隔离和保留期限如何处理。

对初学项目，先持久化 `goal`、`decisions`、`artifacts`、`completed`、`blocked`、`next_action` 等结构化状态，通常比把所有历史对话都做向量检索更可控。

## 8. Multi-Agent 不天然优于 Single Agent

### PDF 表达

PDF p3-p4 一方面指出早期 Multi-Agent 可能不如简单 Single Agent，另一方面称 Agent Teams 可成倍提升效率且 Agent 间不冲突。

### 严谨判断

这两个说法需要用适用条件连接起来。并行可能有效的条件包括：

- 子任务彼此独立或依赖关系清晰；
- 每个 worker 有隔离的上下文和写入范围；
- 结果有结构化协议并可由主流程验证；
- 并行节省的时间大于协调、重复探索和合并成本。

Agent Teams 不会自动消除冲突。多个 Agent 仍可能同时修改同一文件、基于不同假设工作或产生互相不兼容的方案。需要工作区/分支隔离、所有权划分、冲突检测和最终集成验证。

### 工程判断

先得到 Single Agent 的质量、耗时和成本基线。只有当任务可以安全拆分，并且实验显示并行方案更好时，才保留 Multi-Agent。上下文隔离和压缩回传是重要价值，但不必把所有任务都升级为团队模式。

## 9. Docker 是 Sandbox 的一层，不是完整答案

### PDF 表达

PDF p4 认为使用 Docker 作为 Sandbox 可以应对绝大多数场景。

### 严谨判断

Docker 对文件系统、进程和资源隔离很有帮助，但安全结果取决于配置。高风险配置仍可能暴露：

- 宿主目录或 Docker socket；
- 密钥和环境变量；
- 无限制网络访问；
- 过高 Linux capabilities 或特权模式；
- CPU、内存、磁盘和进程资源；
- 不可信镜像、依赖和内核攻击面。

入门项目至少还应具备路径白名单、命令限制、超时、资源上限、网络策略、敏感信息过滤、审计日志和高风险动作确认。用户未准备 Docker 时，可以先在专用临时目录中验证应用层边界，但不能把它宣传为强安全隔离。

## 10. Eval 和 Prompt 优化不能只靠一个指标

### PDF 表达

PDF p4 建议关注 Agent 效果评估，并通过设计指标和观测进行提示词优化。

### 补充边界

这个方向正确，但需要防止对少量示例过拟合。一个最小评测应区分：

- 任务成功率和最终结果正确性；
- 工具选择、参数和执行错误；
- 安全违规与越界尝试；
- 步数、延迟、Token 或费用；
- 环境/API 故障与 Agent 逻辑故障。

固定开发集用于迭代，保留未参与调参的测试集做最终比较。每次只针对清楚的失败模式修改 Prompt、工具或状态机，并做回归测试。指标提升如果以安全下降、成本暴涨或特例规则堆积为代价，也不算真正改进。

## 阅读 PDF 时应保留的价值

完成纠偏后，PDF 中仍有三点值得作为学习主线：

1. 先用极简实现看清 Agent 循环，再选择框架。
2. 工具数量不是能力指标，少量通用工具可以完成很多任务。
3. Coding Agent 比普通聊天 Demo 更容易展示工具、安全、上下文、评测和工程化能力。

使用这三点时，应同时保留可验证证据和适用边界：实现要能运行，结果要能评测，观点要标明来源，未完成的能力不要写成已实现。
